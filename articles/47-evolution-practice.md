## 1. 版本演进：先站稳一个基线

仓颉发行分三档（本仓库 `specs/version-strategy.md` 的口径）：

| 档 | 定位 | 更新 | 适合 |
|---|---|---|---|
| **LTS** | 长期支持 | 慢、稳定、只修不破坏 | 生产/教学/本系列 |
| **STS** | 标准技术演进版 | 快、带新特性 | 追新、尝鲜 |
| **Nightly** | 每日构建 | 极快、不稳定 | 编译器开发者 |

**本系列全程锁 1.0.5 LTS**（当前最新 LTS；STS 已到 1.1.x 线）。为什么锁 LTS、且写进每篇"版本信息"：

1. **可复现**：所有实测结论（41 的 `as` 返回 Option、42 的 `unreachable pattern`、45 的 `MemoryOrder` 弃用……）都绑定一个确定版本，读者环境一致才谈得上"照着跑对得上"。
2. **不被静默打断**：LTS 不破坏 API；追 STS 会碰到"上周的写法这周弃用"。
3. **诚实边界**：1.0.5 的一些"缺失"（无 `cjpm fetch`、无 `cjpm publish`、无 `Channel`/`actor`、内存序不公开）是**版本事实**，本系列如实写，不拿"未来版本会有"糊弄当下。

> **⚠️ 版本检查纪律**：SDK 换版（尤其 1.0 → 1.1 跨线）时，要重跑本仓库的 `tools/test-local.sh` + CI，把每篇"版本信息"复核一遍。**弃用告警是升级的第一手信号**（文章 45 的 `MemoryOrder` 弃用就是 CI 先报出来的）。

## 2. 设计取舍：仓颉"为什么长这样"

把 41–46 的实测点，还原成语言设计层面的取舍。每条括号里是**本篇给的解释（观点）**，前面章节是**事实**。

### 2.1 强类型、零隐式转换 → 用打字换"读代码零歧义"（41）

`Int64→Int32` 不自动、`Int64+Float64` 直接拒。**代价**：样板多。**收益**：任何一处跨界都写在脸上（`Int32(x)`），review 一眼看见"这里在截断"。（取舍：**宁可啰嗦，不要暗改**。）

### 2.2 名义子类型 + struct 不进子类型格 → 可推性优先（41/44）

只有 `class`/`interface` 进子类型关系，`class C <: struct` 被拒；`override` 要显式 `open`。（取舍：**放弃结构类型的"顺手"**，换"继承关系全在声明里、编译器与人都能一眼推定"，也让 struct 保持固定大小的纯值语义。）

### 2.3 ADT + 穷尽性 + Option 不解包 → 把运行期错误提前到编译期（42）

少一个 `case` 编译失败（`non-exhaustive patterns`）、`let Some(v)=…` 因"可反驳"被拒、`Option<Int64>+1` 非法。（取舍：**用"编译期多管一点"**，把 null/未覆盖分支这类 NPE 重灾区变成"根本编不过"。）这是仓颉和"一个 `null`/`Optional` 满天飞"的语言最大的分野。

### 2.4 GC + 值/引用二分 + 无 move/借用 → 选 Java/Go 心智，不选 Rust（44/45）

有 GC、赋值按"值拷贝 / 引用共享"、默认无借用检查（`--enable-borrows` 实验性）。（取舍：**放弃 Rust 的零成本无 GC**，换"没有生命周期标注、上手门槛低、运行时行为接近 Java/Go"。）对**大规模团队和快速开发**，这是比 Rust 更务实的一档；代价是**放弃无 GC 的实时性/可预测延迟**。

### 2.5 `Array` 名值实引用 + 另设 `VArray` → 务实的双轨（44）

`Array` 声明是 struct 但共享 backing（官方原话），另给 `VArray<T,$N>` 做"真值数组"。（取舍：**没有强行二选一**，而是承认"多数场景要 `Array` 的动态+共享、少数热点要零堆定长"，两条都给。代价是"Array 到底拷不拷"得记一条规则——本篇 44 §4 专门拆。）

### 2.6 原子操作不公开内存序（`MemoryOrder` 弃用）→ 心智负担压倒极致调优（45）

只有 `store(v)/load()`、没有 `Acquire/Release/Relaxed` 可选。（取舍：**默认最强、干脆不给降级**，牺牲无锁库实现者的微调空间，换"业务开发不会因选错内存序写出玄学 bug"。）

### 2.7 工具链命名对齐 `cargo` → 降迁移成本（36）

`cjpm` 子命令几乎一一对应 `cargo`（init/build/run/test/tree/update + `target/`）。（取舍：**主动"像现有生态"**，让 Rust/Go 开发者零成本迁移心智——学习曲线也是设计目标。）

> **一句话总纲**（观点）：仓颉在"表达力/极致性能"与"**可推性/低心智负担**"之间，**系统性地偏后者**——强类型、穷尽匹配、名义子类型、SeqCst-only、GC 而非借用，全是同一个方向的不同投影。它想当"**有现代类型系统的、Java/Go 级别的工程语言**"，而不是" Rust 第二"。

## 3. 兼容性与迁移注意

- **LTS 内**：预期 API 不破；新写法多用、弃用项（如 `MemoryOrder`）会被 CI 警告——**看到 `is deprecated` 就要排期改**。
- **跨大版本**（如 1.0.x → 1.1.x）：警惕三类：① 弃用项被**移除**；② 标准库补齐当前"缺口"（本系列标注的 stdx 类：HTTP/WebSocket/JSON 序列化在别处分层）；③ 工具链行为（cjpm 依赖格式等）演进。迁移**必须**重跑 `test-local` + CI。
- **std vs stdx 分层**（承 30）：base `std` 精简稳定、`stdx` 扩展按需；写库要清楚依赖落在哪层（本系列凡 stdx 都明确不臆造）。
- **本系列的"缺口"记录**：1.0.5 无 `cjpm fetch`/`cjpm publish`/内建 `Channel`/`actor`/细粒度内存序——这些**不代表语言永远没有**，但**代表当前写法要绕行**（CLQ、`.cjo`+`--import-path` 分发等）。

## 4. 工程实践清单（把全系列拧成 checklist）

**项目结构**（15/36）：`cjpm init` 起、`src/<pkg>` 分包、包名 `<模块>.<子包>`、`cjpm.toml` 钉 `cjc-version`、`cjpm.lock` 入库。

**类型与正确性**（41–43）：
- [ ] 优先 `enum` + `match` 穷尽表达状态，少用布尔标志位堆叠
- [ ] 可能缺失用 `Option<T>`、禁止"约定式哨兵值"
- [ ] 数值跨界一律显式 `T(e)`，别指望隐式转
- [ ] 纯计算可上 `const func` 让热常量编译期折叠（43）

**内存与并发**（44–45）：
- [ ] 小对象、短生命周期优先 `struct`（少进 GC）
- [ ] 记住 `Array` 是**别名**、赋值不拷——要独立就 `.clone()`、要定长零堆就 `VArray`
- [ ] 跨线程共享走 `Mutex`/`Atomic`/`ConcurrentLinkedQueue`；**`isEmpty`+`remove` 是 race**，用 `match (q.remove())`
- [ ] 资源用 `try-with-resources`（21），**别**指望 `~init`/GC 按时释放

**质量与构建**（35/38/39/46）：
- [ ] `cjpm test` + `@Test`/`@Expect`/`@Assert` 起步就写测试；`cjpm test --coverage` + `cjcov`
- [ ] `cjfmt`（幂等）+ `cjlint` 进 CI 当质量门；`cjpm build -l` 让"要求"级规范挡构建
- [ ] 发布构建 `-O2`/`--lto=thin`；`--int-overflow=wrapping`/`--fast-math` **有语义代价**、须 profile 支撑
- [ ] 性能改动**一律 `cjprof` 前后对比**（46），拒绝"凭感觉优化"

**版本与协作**：
- [ ] 项目锁 LTS、`cjpm.toml` 写 `cjc-version`
- [ ] 升级换版：重跑 `test-local` + CI + 逐篇复核"版本信息"
- [ ] 弃用告警**清零**再发布

## 5. 与其它语言定位对照（观点归纳）

| | 心智最像 | 关键区别 |
|---|---|---|
| 仓颉 | Java / Go（GC、名义子类型、工程语言） | 多了 Rust 级 **ADT + 穷尽 match + Option**（42） |
| vs Rust | — | 无 move/借用/GC 可选、无细粒度内存序（更省心、少极致） |
| vs Go | 都很像 | 仓颉强类型 + 泛型不变 + 无 `interface{}` 满天飞、有 GC 但类型更严 |
| vs Java | 最像 | 仓颉把 `null` 换成 `Option`、隐式数值转换砍掉、值/引用二分更明确 |

**定位判断**（明确是观点）：仓颉像"**给 Java/Go 换上了一套 Haskell/Rust 的类型武器库，但保留 GC 和低心智负担**"。适合想要"类型安全 + 现代语法 + 不用跟借用/内存序搏斗"的团队。

## 6. FAQ

### Q1: 该锁 LTS 还是追 STS？

生产/教学锁 **LTS**（本系列口径）；追新特性、能扛 API 变动再用 STS。混用时**每篇文章/每个模块标清基线**。

### Q2: 仓颉是不是"小 Rust"？

不是（本篇观点）。它借了 Rust 的 **ADT/穷尽/Option**（42），但在**内存管理上选了 GC + 无借用**（44）、**并发上不公开内存序**（45）——是"低心智负担的工程语言"，不是"零成本抽象"。

### Q3: 为什么 1.0.5 连 `Channel` 都没有？

版本事实（45）。当下用 `ConcurrentLinkedQueue` + 手写；未来 STS/新版本可能补。**当下**的教程不该假装它有——本系列的原则是**实测缺就写缺**。

### Q4: 老代码用 `Array` 到处传、发现互相串改怎么办？

这正是 `Array` 别名语义（44 §4）。传出去怕被改就 `.clone()`；想彻底值语义用 `VArray`。把"这是共享引用"写进 code review checklist（§4）。

### Q5: 升级 SDK 最该先看什么？

**CI 的弃用告警**（`is deprecated`）+ 编译错 diff。本系列在 article-45 就是靠 CI 提前发现 `MemoryOrder` 弃用；升级时全量重跑 `test-local` + CI 是最省事的回归网。

### Q6: 系列里这些"设计取舍"是你编的吗？

不是。取舍的**事实**（哪个报错、哪个弃用、哪个不存在）都在 41–46 用 `cjc`/CI 实测；本篇只是把这些事实**归纳成设计方向**。纯判断处（"偏可推性"）明确标了是观点。

## 7. 总结（阶段四收官）

1. **版本**：本系列锁 1.0.5 LTS；LTS/STS/Nightly 分工清楚，**每篇绑定版本 + 升级重跑回归** 是纪律。
2. **设计主线**：仓颉系统性偏"**可推 + 低心智负担**"——强类型/穷尽匹配/名义子类型/SeqCst-only/GC 无借用，都是同一取向（2.x 每条对应一篇实测）。
3. **定位**：像"带上 ADT/Option 的 Java/Go"，不是 Rust 第二（观点，附理由）。
4. **兼容性**：LTS 内稳、跨版本重跑、弃用告警清零再发；std/stdx 分层与 1.0.5 的"当前缺口"如实面对。
5. **落地**：§4 的工程清单是全系列的"带走版"——结构/正确性/内存并发/质量构建/版本协作五组 checkbox。
6. 本篇与文章 37 同为**无 CI 运行示例**的综述篇；事实回指实测篇、观点如实标注。
