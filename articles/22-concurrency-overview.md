# 仓颉并发模型概述

> **摘要**: 仓颉提供**抢占式的线程模型**做并发，实现上是 `M:N` —— M 个"仓颉线程"（用户态轻量线程）在 N 个 native（操作系统）线程上调度。开发者平时只需**面向仓颉线程编程**，用 `spawn` 发起一个任务、拿回一个 `Future`，再用 `get()` 收敛结果，不必关心底层调度。本文依据仓颉 1.0.5 LTS 官方并发概述，讲清语言线程与 native 线程的区别、`1:1` 与 `M:N` 模型、仓颉线程的阻塞与再调度、跨语言调用 foreign 函数的注意事项，并用一个"确定性输出"的最小示例展示任务生命周期。线程的创建/访问/终止/睡眠与锁等同步原语留待后续两篇展开。

## 1. 两种"线程"：语言线程与 native 线程

仓颉的并发基本执行单位是**线程**，但"线程"有两层含义：

- **语言线程**：并发模型的**基本执行单位**，是语言层面的概念。仓颉把它具体化为**仓颉线程**，让开发者无需关心"操作系统线程 / 用户态线程"的差异。
- **native 线程**：语言实现所依赖的底层载体，通常是操作系统的线程。语言线程最终跑在 native 线程上。

大多数时候，你**只面向仓颉线程写并发代码**。

## 2. 1:1 与 M:N 线程模型

不同语言用不同方式把"语言线程"映射到"native 线程"：

| 模型 | 含义 | 代表 |
|---|---|---|
| **1:1** | 每个语言线程直接对应一个 OS 线程（`pthread_create` 等） | 早期 Java 线程、C++ `std::thread` |
| **M:N** | M 个语言线程在 N 个 native 线程上**切换执行**（M、N 不一定相等） | Go（goroutine）、Erlang、**仓颉** |

**仓颉采用 `M:N` 模型**：仓颉线程本质是一种**用户态的轻量级线程**，**支持抢占**，且**比操作系统线程更轻量**——所以你可以随手 `spawn` 成千上万个任务而不炸。

## 3. 仓颉线程如何被调度

关键机制（理解了这些，很多"为什么"就有答案）：

- 每个 native 线程**不断地挑选一个就绪的仓颉线程**来执行。
- 多个仓颉线程可以由**同一个** native 线程执行。
- 当某个仓颉线程在执行中**阻塞**（例如等待互斥锁释放），native 线程会把它**挂起**，转去调度下一个就绪的仓颉线程。
- 阻塞的仓颉线程**重新就绪后**，会继续被 native 线程调度执行。

> **💡 提示**：这正是"轻量级 + 抢占"的价值——一个任务卡在锁上，不会把整条 native 线程占死，其他任务照样推进。

## 4. 跨语言时的坑：阻塞式 foreign 调用

M:N 模型有一个必须注意的例外：**当你调用可能阻塞的 `foreign` 函数（尤其是 IO 相关的系统调用）时，被阻塞的是承载它的那条 native 线程**，而不仅仅是那个仓颉线程。native 线程阻塞期间**无法再调度其他仓颉线程**，吞吐会被拖累。

```cangjie
foreign socket_read(sock: Int64): CPointer<Int8>

let fut = spawn {
    let sock: Int64 = ...
    let ptr = socket_read(sock)   // 进入 foreign 后系统调用阻塞整条 native 线程
}
```

> **⚠️ 注意**：跨语言（C 互操作）时，谨慎在仓颉线程里调用会阻塞的 foreign 函数。这属于并发与互操作交叉的进阶话题，本篇先立个警示，细节见《仓颉-C 互操作》与《并发模型与内存模型》。

## 5. 任务的生命周期（最小模型）

在仓颉里，最常见的并发动作是 `spawn`：把一段闭包作为**任务**发起，运行时返回一个 `Future` 代表"还没算出来的结果"。

```cangjie
let fut: Future<Int64> = spawn { 1 + 2 }
let v: Int64 = fut.get()   // 阻塞直到任务算完，返回 3
```

一个任务大致的生命周期：

1. **创建**：`spawn { ... }` 产生一个仓颉线程/任务，立刻返回 `Future`。
2. **就绪/运行**：被某条 native 线程调度、抢占式执行。
3. **（可能）阻塞与再调度**：遇锁等阻塞时让出 native 线程，就绪后再被调度。
4. **产出结果**：任务体结束，值进入 `Future`。
5. **收敛**：调用方用 `get()` 阻塞取得结果——**把不确定的调度收敛成确定的输出**。

> 官方在文档里说明：**没有歧义时会直接用"线程"指代"仓颉线程"**。本文遵循这一约定。

## 6. 为什么本篇的输出是"确定的"

并发程序最怕"每次跑结果不一样"。诀窍是：**并行的部分交给 `spawn`，输出的部分靠 `get()` 串行收敛**。只要每个结果在被 `println` 前都 `get()` 过，输出就与调度顺序无关。

反例是"两个任务不同步地往同一共享变量写"——那是数据竞争，结果不确定，需要锁/通道（下一篇《同步与并发原语》处理）。本篇刻意**不使用**未同步的共享可变状态，因此输出完全确定。

## 7. 完整可运行示例

下例发起两个任务（求和、求阶乘），主线程用 `get()` 阻塞收敛——输出与调度顺序无关。

<!-- example: cangjie/027-concurrency-overview.cj -->
```cangjie
// 并发模型概述示例
// 演示：以 spawn 创建"任务"（返回 Future）、任务被 native 线程调度、用 get() 阻塞取结果，
// 体现 M:N 抢占式线程模型下"面向仓颉线程编程"的基本形态，并说明输出为何与调度顺序无关。
//
// 说明：线程的创建/访问/终止/睡眠与锁等同步原语在下一篇《线程与协程使用》《同步与并发原语》展开；
// 本篇只用最小的 spawn + Future.get() 演示"任务生命周期"，且保证结果确定。

main(): Int64 {
    // 任务 1：计算 1..=100 的和。spawn 之后不立即等待，让调度器有机会并行推进。
    let futSum = spawn {
        var s = 0
        for (i in 1..=100) {
            s += i
        }
        s
    }

    // 任务 2：计算 10 的阶乘。两个任务由运行时在 native 线程上调度（可能并行）。
    let futFact = spawn {
        var p: Int64 = 1
        for (i in 1..=10) {
            p = p * i
        }
        p
    }

    // get() 会阻塞当前（主）线程直到对应任务算出结果。
    // 因此下面两行的输出完全确定，与两个任务被调度的先后无关。
    println("sum(1..=100) = ${futSum.get()}")     // 5050
    println("10! = ${futFact.get()}")             // 3628800

    // 结论：spawn 让开发者只面向"仓颉线程/任务"编程，无需关心底层 M:N 与 native 线程；
    // 通过 Future.get() 把"不确定的调度"收敛为"确定的结果"，是并发最基础的用法。
    return 0
}
```

预期输出：

```text
sum(1..=100) = 5050
10! = 3628800
```

## 8. 语言对比

| 维度 | 仓颉 | Go | Java（虚拟线程前） | Rust |
|---|---|---|---|---|
| 模型 | 抢占式 `M:N`（仓颉线程） | 抢占式 `M:N`（goroutine） | `1:1`（OS 线程）；Loom 后 `M:N` | `1:1`（`std::thread`）；异步靠运行库 |
| 轻量单位 | 仓颉线程 | goroutine | 线程较重；虚拟线程较新 | 需 tokio/async-std 等 |
| 发起并发 | `spawn { ... }` → `Future` | `go f()` | `new Thread(..)` / Executor | `thread::spawn` / `tokio::spawn` |
| 取结果 | `future.get()`（阻塞） | channel / WaitGroup | `Future.get()` / `join()` | `join()` / `await` |
| 抢占 | 支持 | 支持 | OS 级抢占 | 线程抢占；异步需 yield |
| 阻塞 foreign/系统调用 | 会占住 native 线程（需注意） | 类似（cgo 有专门处理） | — | — |

**从 Go 迁移**：`spawn { }` ≈ `go func(){}()`，`Future.get()` ≈ 从 channel 收值；差别在仓颉把"结果"建模成 `Future` 而非 channel。
**从 Java 迁移**：仓颉线程天生轻量（M:N），不像传统 `Thread` 那样一条对应一个 OS 线程，可大量并发。

## 9. 常见问题（FAQ）

### Q1: 仓颉线程就是操作系统线程吗？

不是。仓颉线程是**用户态轻量线程**，由运行时在若干 native（OS）线程上调度（M:N）。你可以创建大量仓颉线程而不会像 OS 线程那样很快耗尽资源。

### Q2: "抢占式"意味着什么？

意味着单个仓颉线程不会因为你没主动让出就一直独占 native 线程——运行时会调度切换，一个任务阻塞时 native 线程会去跑别的就绪任务。

### Q3: `spawn` 返回什么？怎么拿结果？

返回一个 `Future`；调用 `get()` 会阻塞当前线程直到任务完成并产出结果。

### Q4: 并发程序怎么保证输出稳定？

让每个要输出的值都经过 `Future.get()` 等"收敛点"，或做适当同步；不要在没同步的情况下让多任务并发改同一变量（数据竞争）。

### Q5: 为什么跨语言要担心 foreign 调用？

阻塞式 foreign 调用会占住整条 native 线程，期间该线程不能再调度其它仓颉线程，降低吞吐。

### Q6: 线程的创建细节、锁、通道在哪篇？

在《线程与协程使用》《同步与并发原语》两篇；调度与内存模型原理在《并发模型与内存模型》。

## 10. 总结

1. 仓颉并发是**抢占式线程模型**；执行单位分**语言线程（仓颉线程）**与 **native 线程**两层。
2. 实现是 **`M:N`**：M 个轻量仓颉线程在 N 个 OS 线程上调度，**支持抢占**，比 OS 线程轻。
3. native 线程挑就绪的仓颉线程执行；仓颉线程阻塞时让出、就绪后再被调度。
4. 平时**面向仓颉线程编程**；跨语言时警惕阻塞式 `foreign` 调用占住 native 线程。
5. 最小用法：`spawn { ... }` 得到 `Future`，`get()` 阻塞取结果——把不确定的调度收敛成确定的输出。
6. 具体的线程 API、同步原语、调度/内存模型分别由后续专题承接。
